# ADR-005: Gestione Media, Vincoli Relazionali e Integrità Referenziale

## Stato
Accettata e allineata al codice effettivo.

## Contesto
La piattaforma "La Nostra Città, Il Nostro Futuro" gestisce segnalazioni civiche corredate da prove multimediali (foto/video). Il modello logico originale e i requisiti impongono:
1. Che ogni segnalazione sia associata ad almeno un media valido nello stato READY.
2. Che le elaborazioni e analisi automatiche (`AnalisiIa`) riferite a uno specifico media appartengano rigorosamente alla stessa segnalazione del media stesso, prevenendo disallineamenti o incroci indebiti.
3. Lo stack autorizzato è **Next.js + Prisma + MySQL su Aiven** (non PostgreSQL).

## Decisioni Architetturali e di Integrità

### 1. FK Composta Media/AnalisiIa (Garanzia a livello DB)
- In MySQL InnoDB, l'integrità tra `AnalisiIa` e `Media` è garantita direttamente dal database engine tramite un vincolo di Foreign Key composto:
  `FOREIGN KEY (media_id, segnalazione_id) REFERENCES Media(id, segnalazione_id) ON DELETE RESTRICT ON UPDATE CASCADE`
- La tabella `Media` espone il vincolo `UNIQUE (id, segnalazione_id)`.
- **Garanzia**: È fisicamente impossibile a livello DB inserire un'analisi IA che associ un media appartenente a una diversa segnalazione.

### 2. Vincolo Minimo sui Media (Regola Applicativa Transazionale)
- Il vincolo di cardinalità minima ("ogni segnalazione deve avere almeno un media valido READY") è implementato come **garanzia applicativa transazionale** all'interno della funzione di dominio `createSegnalazioneAtomica`.
- Al momento della creazione, la richiesta priva di media validi viene respinta immediatamente prima di aprire transazioni o alterare lo stato del database.
- Non vengono usati trigger differibili in MySQL per questa cardinalità: la consistenza è governata dall'unico writer transazionale del dominio.

### 3. Percorsi Realmente Implementati vs Mancanti
- **Implementati**:
  - `createSegnalazioneAtomica`: verifica autore (attivo e verificato), consumo atomico token `UploadTemporaneo`, creazione atomica di `Segnalazione`, `Media` (stato READY con metadati validati dal server), `EventoStato`, `AuditEvento` e `Outbox`.
  - `aggiungiSostegno`: verifica blocco autosostegno (`utenteId !== autoreId`), stato utente (attivo e verificato), stato segnalazione (`APPROVATA`, non ritirata), e inserimento/upsert idempotente in `Sostegno`.
- **Mancanti / Non Esposti**:
  - **Rimozione media / Ultimo media**: Il percorso di rimozione di allegati da una segnalazione è **attualmente NON IMPLEMENTATO**. Nessuna API o Server Action di cancellazione o modifica non protetta dei media è esposta, garantendo che nessuna segnalazione esistente possa essere lasciata priva di prove probatorie.

### 4. Gestione Retry e Background Jobs
- Si dichiara esplicitamente che **non sono presenti sistemi o loop di retry in background**.
- I campi `tentativi` e `prossimo_tentativo_il` nelle tabelle `Outbox` e `AnalisiIa` sono predisposizioni di schema. Nessun worker o demone di riesecuzione è implementato o spacciato per collaudato.

### 5. Rilevazione Versione Server MySQL
- La versione esatta del database server MySQL deve essere rilevata in runtime direttamente dal servizio (`SELECT VERSION();`) e non dedotta da parametri statici di configurazione o assunzioni documentali.
